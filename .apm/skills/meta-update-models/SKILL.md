# Update Models Skill

Reads a `metadata.modelProfile` block from any customization file that supports the top-level `model` frontmatter field and produces **two** things:

1. **The active Claude Code fields** — a single `model:` alias and an `effort:` value, resolved **deterministically** from the profile (no network needed). These are the only functional model-selection fields, because Claude Code is the primary harness and its `model:` field takes a single alias, not an array.
2. **A non-functional multi-provider candidate list** — an ordered comment block, regenerated by fetching the authoritative model catalogues from **all supported providers in parallel** and applying the filter/rank logic below. This preserves cross-harness intent for reference; no harness reads it.

> **Why the split:** Claude Code's `model:` accepts a single alias (`sonnet`/`opus`/`haiku`/`fable`), a full model ID, or `inherit` — see [sub-agents docs](https://code.claude.com/docs/en/sub-agents). VS Code Copilot's `model:` takes provider-suffixed display strings (single or array). The two formats are **disjoint**: no single string is valid in both. This repo optimizes for Claude Code (active fields) and keeps the Copilot/multi-provider ranking as a comment.

`cost`, `latency`, and `specialisation` are abstract tiers. The active fields map them via the fixed tables below; the candidate list maps them to each provider's pricing/entitlement model at run-time (approximate — see Step C2).

Use the current on-disk file contents as the only source of truth. Read every target file before changing it, apply the edit, and verify the saved file before reporting completion. Never describe a proposed selection as if it has already been applied.

## Authority and Freshness

- Treat live provider docs and API responses as higher authority than examples in this skill
- Prefer current provider capability labels and product guidance over hard-coded model families
- Treat concrete model names in examples as illustrative snapshots only; do not encode them as durable ranking rules
- The **active `model:` alias and `effort:`** come from the deterministic maps (Part A), not from live docs — aliases auto-track the current model generation

## Supported Scenarios

- User asks to "update models", "refresh model lists", or "regenerate model arrays"
- A customization file both supports the `model` frontmatter field and contains a `metadata.modelProfile` block, but the active `model:`/`effort:` or the candidate comment is stale or missing
- Bulk-refreshing every agent to bring the whole repo up to date

## Process

### Step 1 — Validate the target and read the profile

Read the target file, confirm it supports the top-level `model` frontmatter field, and extract `metadata.modelProfile`:

```yaml
metadata:
  modelProfile:
    specialisation: NONE   # NONE | CODE | REASONING | LONG-CONTEXT
    cost: MEDIUM           # FREE | LOW | MEDIUM | HIGH
    latency: LOW           # LOW | MEDIUM | HIGH
    minDate: "2025-01-01"
```

If no `modelProfile` is present, or the file does not support the `model` frontmatter field, stop and ask the user how to proceed, using a tool if available.

---

## Part A — Resolve the active Claude Code fields (deterministic, no fetch)

These are the **functional** fields. Apply the fixed maps below; do not fetch.

### Step A1 — `model:` alias from `cost`

| `cost` | `model:` alias |
|--------|----------------|
| `HIGH` | `opus` |
| `MEDIUM` | `sonnet` |
| `LOW` | `haiku` |
| `FREE` | `haiku` |

Use aliases (not full model IDs) so the value auto-tracks the current generation and needs no churn. Use `inherit` **only** for an agent that must deliberately follow the session model (record the intent in a comment); the default is the cost-mapped alias.

### Step A2 — `effort:` from `specialisation` + `latency`

| profile signal | `effort:` |
|---|---|
| `specialisation: REASONING` | `high` (→ `xhigh` when `cost: HIGH`) |
| `latency: HIGH` | `high` |
| `latency: MEDIUM` | `medium` |
| `latency: LOW` | `low` |

`specialisation: REASONING` overrides the latency row. `effort` is a Claude-Code-only field with values `low | medium | high | xhigh | max`.

---

## Part B — Regenerate the candidate comment list (live fetch)

The output of Part B is a **comment block only** — it is not read by any harness. Keep it useful and current, but never place it in an active `model:` field.

### Step B1 — Fetch all providers in parallel

Fetch the model catalogue from **every supported provider** concurrently. The URLs are listed in this skill's `metadata.provenance.authoritativeSpec`. Do not rely on cached data — these pages change frequently.

| Provider | What to extract |
| --- | --- |
| **GitHub Copilot** | Display name, premium request multiplier, release status, retirement date, training date, plan inclusion, task guidance |
| **Claude Code** | Current Claude model names/families, availability or entitlement notes, usage/cost notes, and model-role guidance from Anthropic docs |
| **OpenAI Codex** | Current OpenAI model names/families available through Codex, including non-Codex models, plus availability or entitlement notes, usage/cost notes, preview status, and model-role guidance |
| **KiloCode** | `id`, `name`, `isFree`, context length, pricing fields, release status, and training date/knowledge cutoff fields when present |

> To add a new provider: fetch its model docs, add the URL to `metadata.provenance.authoritativeSpec` in this file, update `CONTRIBUTING.md`, and add its entitlement/cost-band mapping to Step B2.

### Step B2 — Map cost bands to provider metrics

Translate the abstract `cost` tier to each provider's pricing or entitlement model. **This mapping is approximate** — pricing structures differ across providers and change over time. Use the table below as a starting point, but treat the boundaries as fuzzy:

| Cost tier | GitHub Copilot | Claude Code | OpenAI Codex | KiloCode |
| --- | --- | --- | --- | --- |
| `FREE` | Multiplier = 0; qualifying entries belong in the free-first prefix | Only models explicitly documented as zero-burn or otherwise truly free-to-use. Do **not** treat bundled subscription usage as `FREE` | Only models explicitly documented as zero-burn or otherwise truly free-to-use through Codex. Do **not** treat bundled subscription usage as `FREE` | `isFree = true` or all relevant pricing fields are `0` |
| `LOW` | Multiplier ≤ 0.33 | Lowest-burn models documented as available | Lowest-burn models documented as available through Codex | **Not allowed** |
| `MEDIUM` | Multiplier ≤ 1 | Standard generally available models with moderate usage burn | Standard generally available models with moderate usage burn through Codex | **Not allowed** |
| `HIGH` | Any multiplier | Any documented premium or add-on tier available | Any documented premium, preview, or credit-backed tier available through Codex | **Not allowed** |

Interpret `cost` as a **ceiling**, not as an instruction to maximize cheapness. Once candidates are inside the allowed cost band, task fit and specialization outweigh small cost savings.

Assume the user has **GitHub Copilot**, **Claude Code**, and **OpenAI Codex** subscriptions available. Do **not** treat models merely included in those subscriptions as `FREE`. By contrast, **KiloCode is hard-capped to truly free models only** — never spend KiloCode credits and never relax KiloCode above `isFree=true`.

**When the mapping is unclear**, do a targeted web search (e.g. `"KiloCode free models"`, `"OpenAI models available in Codex"`, `"Claude Code available models"`). Prefer recent community sources, changelogs, or official blog posts. Note any uncertainty in the summary reported to the user.

### Step B3 — Filter (per provider)

For each provider's catalogue, apply these filters **in order**, discarding models that fail any check:

| Filter | Rule |
| --- | --- |
| **Retired / unavailable** | Exclude any model with a retirement date on or before today's date, or any model no longer listed as available in the relevant product docs |
| **Training Date** | Exclude any model trained before `minDate`; ensures intrinsic knowledge up to that date |
| **Entitlement** | For Claude Code and OpenAI Codex, keep only models the current docs or user context show as available; for Copilot, keep models available; for KiloCode, keep only free models |
| **Cost band** | Apply the provider-specific mapping from Step B2. KiloCode remains free-only even when the profile cost is higher |
| **Specialisation** | `CODE` → keep only models described as code-optimised, coding-specialised, or agentic-coding-oriented in the docs, falling back to clear family identifiers only when the docs lack richer labels; `REASONING` → keep only models explicitly labeled for reasoning, thinking, deep debugging, or similar deliberate-reasoning tasks; `LONG-CONTEXT` → keep only models with context windows ≥ 200K tokens, sorted by context window size (largest first); `NONE` → keep all remaining models |
| **Task match** | Based on the agent's task descriptions, ensure the model is appropriate for that type of task using the product guidance in the fetched docs |

Apply the same capability bar to free and paid candidates. For `LOW`, `MEDIUM`, and `HIGH` profiles, a free candidate must be **explicitly validated as competitive** with the paid candidates for that task. "Acceptable" is not sufficient.

### Step B4 — Format model names

Format each model's display name and append the provider suffix used by this repository. Use the **exact accepted display strings**; preserve spelling and casing exactly; do **not** normalize names across providers when the working display strings differ. If the same working model name already appears elsewhere in the workspace, reuse that exact spelling/casing unless you have evidence it is broken.

All model names in this section are illustrative examples only. Always use the current names returned by the fetched live documentation or API.

- **GitHub Copilot:** exact display name from official docs, append ` (copilot)`.
- **Claude Code:** exact accepted unify-provider display name, append ` (unify-chat-provider)`. Usually omits vendor prefixes.
- **OpenAI Codex:** exact accepted unify-provider display name, append ` (unify-chat-provider)`. Usually omits vendor prefixes.
- **KiloCode / unify-backed non-Copilot entries:** start from the API/provider display name, **strip** vendor prefixes such as `Anthropic: `, `OpenAI: `, `Google: `, `xAI: `, `MiniMax: `, `Xiaomi: ` unless existing workspace usage shows the prefix is required, then append ` (unify-chat-provider)`.

The same model family can legitimately have different accepted strings across providers — e.g. `GPT-5.4 mini (copilot)` and `GPT-5.4 Mini (unify-chat-provider)` must not be normalized to match.

| API `name` field | Display name |
| --- | --- |
| `OpenAI: GPT-5.4 Mini` | `GPT-5.4 Mini (unify-chat-provider)` |
| `Anthropic: Claude Sonnet 4.6` | `Claude Sonnet 4.6 (unify-chat-provider)` |
| `xAI: Grok Code Fast 1 Optimized (experimental, free)` | `Grok Code Fast 1 Optimized (experimental, free) (unify-chat-provider)` |
| `Xiaomi: MiMo-V2-Pro (free)` | `MiMo-V2-Pro (free) (unify-chat-provider)` |

### Step B5 — Merge and rank

Combine the filtered, suffixed lists into a single ordered pool (the pool the harness *would* pick first-available from, were this field functional).

- For `FREE` profiles, validated free-capable candidates belong first (top KiloCode free model if genuinely good enough; qualifying multiplier-0 Copilot models).
- For `LOW`/`MEDIUM`/`HIGH` profiles, start with the strongest **paid** coverage in this order when candidates remain after cost filtering: top Claude Code-backed → top OpenAI-backed via Codex → top Copilot not already included. Append a free candidate only when explicitly validated as competitive.
- Within each provider group, sort by specialisation/task fit, then latency (`LOW`→smallest/fastest first, `HIGH`→largest/most capable, `MEDIUM`→neutral), then cost (tie-break only), then recency (GA over preview).

**Count rules:** include ≥1 Claude Code-backed, ≥1 OpenAI-backed via Codex, and ≥1 Copilot model when each still has a candidate after filtering; 0 KiloCode by default for non-`FREE` profiles; take the **top 1–8 models total**.

---

### Step C — Write the frontmatter

Emit the three parts in this order, in the "Claude Code fields" region of the frontmatter (after any Copilot-only fields, before `metadata:`):

```yaml
# Claude Code fields
model: sonnet          # from modelProfile.cost (Step A1)
effort: high           # from modelProfile (Step A2)
# Multi-provider candidates — NON-FUNCTIONAL, for reference only.
# Regenerated by meta-update-models from metadata.modelProfile (Part B):
#   - Claude Sonnet 4.6 (unify-chat-provider)
#   - GPT-5.4 (unify-chat-provider)
#   - Claude Sonnet 4.6 (copilot)
#   - GPT-5.4 (copilot)
```

Rules:
- `model:` is a bare single value (alias / full ID / `inherit`), **not** a YAML array.
- The candidate list is a **YAML comment block** (each line prefixed with `#`), never an active field. Preserve the "NON-FUNCTIONAL, for reference only" label so no future edit promotes it to a live array.
- If an old array-style `model: [...]` exists, replace the whole thing with the three-part shape.
- Do **not** modify any other frontmatter fields. Do **not** remove `metadata.modelProfile` — it is the source of truth for future updates.

**Reasoning output (required):** when reporting to the user, state the resolved `model:`/`effort:` and why (which map rows applied), then a brief `+`/`-` justification for each change in the candidate comment vs. the previous list.

## Example

**Profile:**

```yaml
metadata:
  modelProfile:
    specialisation: CODE
    cost: LOW
    latency: LOW
    minDate: "2025-01-01"
```

**Resolution:**

- Active `model:` → `haiku` (cost `LOW`, Step A1).
- Active `effort:` → `low` (not REASONING; latency `LOW`, Step A2).
- Candidate comment (Part B, illustrative — real names come from live docs): top Claude coding model, top OpenAI coding model via Codex, a coding-specialized Copilot model.

**Result:**

```yaml
# Claude Code fields
model: haiku
effort: low
# Multi-provider candidates — NON-FUNCTIONAL, for reference only.
# Regenerated by meta-update-models from metadata.modelProfile:
#   - Example Claude Coding Model (unify-chat-provider)
#   - Example OpenAI Codex Model (unify-chat-provider)
#   - Example Copilot Coding Model (copilot)
```

**Reasoning output:**
- `model: haiku` / `effort: low` — cost `LOW` → `haiku`; non-reasoning, latency `LOW` → `low`.
- `+ Example Claude Coding Model (unify-chat-provider)` — best low-latency Claude coding fit.
- `+ Example OpenAI Codex Model (unify-chat-provider)` — CODE-specialized over a cheaper generic mini within band.
- `- Example Free Model (unify-chat-provider)` — profile is non-`FREE`; free candidate not materially stronger.

## Bulk Updates

To update all supported customization files:

1. List all relevant customization files (`*.agent.md`, `SKILL.md`, `*.prompt.md`, `*.instructions.md`)
2. Keep only files that both contain `metadata.modelProfile` and support the top-level `model` frontmatter field; capture each file's current `model:`/`effort:` and candidate comment from disk
3. For each target file, run Steps 1, A1–A2, B1–B5, C
4. Re-read or diff every changed file before preparing the final response
5. Report a summary table: file → old (model/effort) → new (model/effort) → candidate-list delta

## Constraints

- Always fetch docs fresh for the candidate list — never rely on a cached or remembered model list
- The active `model:`/`effort:` are deterministic (Part A maps) and require no fetch
- Preserve all other frontmatter fields exactly as-is
- Never claim a file was "updated" until the edit has been applied and verified on disk
- If a target file changes after the initial read, re-read it before editing
- If the docs are unreachable, still write the deterministic active fields; report the error and leave the candidate comment unchanged

## Provider-Specific Considerations

These apply to the **candidate comment list** (Part B) only.

### KiloCode Integration

1. **Pricing Data**: Consult `https://api.kilo.ai/api/gateway/models` for current pricing.
2. **Free-only policy**: Only select models where `isFree=true` or all relevant pricing fields are zero. Never relax KiloCode above free. For non-`FREE` profiles, default to excluding KiloCode entirely; include a free model only when genuinely competitive after the normal filters.
3. **Model Naming**: Derive display names from the API `name` field; strip the vendor prefix (everything up to and including `: `). Do NOT use `id` as the display name. Do NOT invent names.
   - ❌ `corethink:free (unify-chat-provider)` — fabricated
   - ✅ `Example Model (unify-chat-provider)` — from API `name: "Vendor: Example Model"`
4. **Model Compatibility**: code agents → models with `code`/`coder` in id or documented as code-optimized; research agents → larger context + general knowledge; general → balance.
5. **Knowledge Cutoff**: Use `training_date`/`knowledge_cutoff` to apply the `minDate` filter.

### Claude Code Integration

1. **Entitlement check**: Derive available Claude models from user context + current docs. Do not treat GA Claude models as `FREE` unless docs mark them zero-burn.
2. **Model Identification**: Use current Claude model names, appending `(unify-chat-provider)` in the candidate list. (The active `model:` alias is separate — from Part A.)
3. **Task Compatibility**: code → balanced/coding-oriented class before the smallest; research → largest context + strongest reasoning; general → balanced default; interactive/UX/planning → balanced or reasoning class on non-`FREE` MEDIUM/HIGH unless clearly lightweight.

### OpenAI Codex Integration

1. **Entitlement check**: Derive available OpenAI models from user context + current Codex/OpenAI docs. Do not treat GA models as `FREE` unless documented zero-burn through Codex.
2. **Model Identification**: Select from the full OpenAI catalogue available through Codex, not only names containing `Codex`. Append `(unify-chat-provider)`.
3. **Task Compatibility**: code → coding-specialized/agentic family first; low latency → lightest that still fits; deep reasoning → strongest within cost tier; reasoning-heavy planning → full reasoning models over mini by default.

### Copilot Integration

1. **Model Identification**: Use display names from official Copilot docs, appending `(copilot)`.
2. **Task Compatibility**: code → coding-specialized before generic mini; research → larger context + recent cutoff; general → balance; reasoning-heavy → deep-reasoning models before mini/latency-first variants.
